# Normative Feature Specification

## 1. Terminology

- **Master**: the setup principal authenticated by `MASTER_KEY`.
- **User**: a master-created person identified by a unique email username.
- **Organization**: a master-created resource and usage boundary.
- **Membership**: a link from a user to an organization with a role.
- **Personal key**: an API key owned by a user without organization context.
- **Organization-scoped personal key**: a user-owned key whose requests execute
  in one organization context.
- **Organization key**: a key owned by an organization and treated as a shared
  organization principal. Its permissions come only from its stored scopes; it
  does not inherit a human membership.
- **Principal**: the authenticated master, user, or organization represented by
  the presented secret.
- **Actor**: the principal snapshot written to an audit or usage event.

`tenant` is legacy terminology. New domain types, APIs, and UI use
`organization`. Compatibility aliases may remain during migration.

## 2. Users

### 2.1 Fields

A user contains:

```text
id
username
normalized_username
status                  active | disabled
created_at
updated_at
```

All IDs and timestamps are generated by the Go backend before persistence.

### 2.2 Username rules

- The username is an email address.
- Normalize by trimming surrounding whitespace and lowercasing.
- Reject an empty or syntactically invalid email address.
- `normalized_username` is globally unique.
- Usernames are immutable in the first implementation. A future rename must be
  a separate audited operation.

### 2.3 Lifecycle

- Only master may create a user.
- Creation may optionally generate an initial personal login key.
- The plaintext key is returned once and never persisted or returned again.
- Normal deletion is a status change to `disabled`, not hard deletion.
- Disabling a user invalidates every user-owned key and active cookie session.
- Historical usage and audit actor snapshots remain unchanged.

## 3. Organizations and memberships

### 3.1 Organization fields

```text
id
name
normalized_name
status                  active | disabled
created_at
updated_at
```

Organization names are trimmed, case-insensitively unique, and master-created.

### 3.2 Membership fields

```text
organization_id
user_id
role                    member | admin
created_at
created_by_actor_type
created_by_actor_id
```

A user may belong to multiple organizations. A user has at most one membership
record per organization.

### 3.3 Membership policy

- Master may add, update, or remove any membership.
- An organization administrator may add an existing active user to their own
  organization, change member roles, and remove members.
- Organization administrators may not create users or organizations.
- An ordinary member may read their own membership but not the full member list
  unless another explicit scope permits it.
- Removing or demoting the last active organization administrator is rejected.
  Master may override only by simultaneously assigning another administrator
  or disabling the organization.
- Removing a membership immediately invalidates that user's organization-
  scoped keys for the organization.
- Disabled users cannot be added to an organization.

## 4. API-key ownership and context

### 4.1 Extended key fields

In addition to the existing ID, name, hash, prefix, models, scopes, quota, RPM,
enabled state, and timestamp, an API key contains:

```text
owner_type                 user | organization
owner_user_id              nullable
owner_organization_id      nullable
context_organization_id    nullable
```

Exactly one owner ID is present and it matches `owner_type`.

### 4.2 Valid key shapes

| Kind | Owner | Context organization |
|---|---|---|
| Personal | User | Empty |
| Organization-scoped personal | User | Organization where user is an active member |
| Organization | Organization | Same organization |

An organization-owned key with a different or empty organization context is
invalid.

### 4.3 Key management policy

- Master may create, inspect metadata, update, rotate, disable, or delete any
  key.
- Users may create and manage only their own user-owned keys.
- A user may create an organization-scoped key only for an organization where
  they are an active member.
- An organization administrator may create and manage organization-owned keys
  for their organization.
- An organization administrator may view safe metadata for user-owned keys
  scoped to their organization but may not rotate, reveal, delete, or change
  ownership of those keys.
- No principal may grant a new key scopes or model access beyond what the
  current principal is authorized to grant.
- Organization membership removal makes affected organization-scoped user keys
  unusable without deleting the key record or its history.
- Key ownership and context are immutable. Changing either requires creating a
  new key and revoking the old one.
- Key rotation preserves ownership, context, models, scopes, quota, and RPM,
  invalidates the previous secret immediately, and returns plaintext once.

### 4.4 New scope

Add the valid scope:

```text
members:manage
```

Membership administration requires both:

- Master, or an active `admin` membership for the target organization.
- `members:manage` on the authenticating key (master bypasses scopes).

Organization-key creation requires `keys:manage`. Organization-wide usage
requires `usage:read`.

An organization key is not automatically omnipotent inside its organization.
It may perform only organization operations allowed by both its scopes and the
object-level organization policy. It can never create users or organizations.

## 5. Authentication and sessions

### 5.1 Login

The existing login endpoint continues accepting a master key or API key. A
username alone is not a credential. There are no passwords.

API-key authentication resolves the owner and context before issuing a signed
session. An enabled key is still rejected when its user, organization, or
required membership is disabled or missing.

### 5.2 Session fields

Sessions include:

```text
principal_type             master | user | organization
key_id
user_id
username
organization_id
membership_role
scopes
expires
```

Do not trust authorization fields only because they were signed earlier.
Cookie sessions are revalidated against current key, owner, organization, and
membership state without extending their original expiration.

### 5.3 Authorization

Every protected operation performs both:

1. A capability/scope check.
2. An object ownership or organization policy check.

Do not use a broad organization/legacy tenant filter as a substitute for
personal key or personal usage ownership.

Unauthorized access to another user's private resource returns 404 where
resource concealment is appropriate. Missing capability returns 403.

## 6. Gateway access context

Refactor gateway request handling away from assuming every request has a stored
API key. Resolve an access context containing:

```text
actor type and snapshot
optional API key
optional user
optional organization
cache namespace
allowed models
quota/RPM policy
credential visibility policy
```

### 6.1 User-owned key

- Enforce the key's model allowlist, RPM, quota, scopes, and enabled state.
- Personal keys use global/shared credentials only.
- Organization-scoped keys may use global/shared credentials plus credentials
  owned by their context organization.
- Cache isolation remains at least key-level by default.

### 6.2 Organization-owned key

- Enforce the key's model allowlist, RPM, quota, scopes, and enabled state.
- Permit global/shared credentials plus credentials owned by the organization.
- Attribute requests to `org:<organization-name>` because a shared key cannot
  identify an individual user.

### 6.3 Master key

Master-key model calls are supported:

- All enabled models are visible.
- All eligible credentials are visible.
- API-key quota and RPM checks are skipped.
- Cache uses a dedicated `master` namespace and does not share personal or
  organization key cache entries.
- Usage actor is `master`.
- `api_key_id` is empty; do not create a synthetic database key.

## 7. Usage events and visibility

### 7.1 Actor fields

Add these immutable fields to usage events and recent-event responses:

```text
actor_type                 master | user | organization | legacy
user_id                    empty when not a user actor
username                   user email, master, org:<name>, or legacy
organization_id            empty for personal/master calls
```

Continue recording existing key, credential, model, upstream model, token,
price, cache, status, duration, and safe error fields.

Actor fields are snapshots. Do not join at render time to derive a historical
username or organization display name.

### 7.2 Visibility

| Principal | Usage visibility |
|---|---|
| Master | All events |
| User | Events whose `user_id` equals the session user |
| Organization admin/key | Events whose `organization_id` equals the active organization |
| Organization member | Own user events only, including own organization-context events |

An organization administrator must never see a member's unrelated personal
usage.

### 7.3 History presentation

The primary usage-history columns are:

```text
Model | User | I/O | Time
```

- `User` uses the actor snapshot.
- `I/O` renders `prompt_tokens -> completion_tokens` with localized integer
  grouping.
- For timestamps from 0 through 59 seconds old, render `N seconds ago`.
- At 60 seconds and older, render UTC RFC3339.
- Future timestamps are clamped to `0 seconds ago` for display.
- Always include exact RFC3339 in a `<time datetime="...">` element.
- Cost, cache token counts, status, duration, API-key metadata, credential, and
  exact timestamp remain available in expandable details.

### 7.4 Querying

Usage APIs support cursor pagination and bounded filters for:

- Time range.
- Organization.
- User.
- Model.
- API key.
- Status.

Repository methods receive a typed visibility/query object. Do not construct
authorization-sensitive SQL fragments from raw query strings.

## 8. Audit events

Administrative activity is separate from model usage. Record:

```text
id
ts
actor_type
actor_id
actor_label
organization_id
action
target_type
target_id
safe_metadata
```

Required actions include user creation/status changes, organization creation/
status changes, membership add/remove/role changes, and key create/rotate/
disable/delete.

Audit metadata must never contain plaintext keys, hashes, OAuth tokens, prompts,
completions, cookies, or authorization headers.

Audit visibility follows the same master/organization boundary as usage.

## 9. Compatibility and migration

- Existing tenant records migrate to organizations while preserving IDs.
- Existing tenant-owned API keys migrate to organization-owned keys.
- Existing credential ownership migrates to organization ownership.
- Existing usage keeps its organization identifier and receives
  `actor_type=legacy`, `username=legacy`, and an empty `user_id`.
- Keep `/admin/tenants` as a deprecated compatibility alias during one release;
  new code and UI use `/admin/organizations`.
- Existing key plaintext does not need regeneration.
- Migrations must not generate IDs or timestamps in the database.
- The Go backend explicitly supplies IDs and times for all new records and
  inserts.

## 10. Security requirements

- Never expose plaintext keys except once at create/rotate time.
- Continue constant-time master-key comparison and hashed API-key lookup.
- Do not log secrets or request prompts/completions.
- Invalidate key caches after key, user, organization, or membership changes.
- Fail closed on malformed owner/context combinations.
- Prevent horizontal access through IDs in URLs, forms, or JSON bodies.
- Perform authorization in handlers/use cases even when the UI hides an action.
- Use explicit typed request/response and persistence structs.
